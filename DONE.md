## Legacy format tracking (2026-08-10)
- [x] `fontctl scan` now recognizes Type 1 (`.pfb`/`.pfa`) and legacy bitmap (`.bdf`/`.pcf`/`.fon`/`.dfont`) files — previously invisible to scan entirely. They get a `font_files` row (path/hash/format), so they show up in `list`/`info` and — since `content_hash` is format-agnostic — **duplicate detection works on them** (verified: two identical `.pfb` files under different names were correctly grouped). No family/style/glyph metadata yet (`parser.py`'s `_parse_unsupported` fallback — real parsing needs `fontTools.t1Lib` for Type 1, nothing usable for bitmap). Every such file gets an `unsupported_format` (severity `info`) `validation_issue` so `fontctl validate` makes the gap visible rather than silent.

## Classification + Backup/Restore (2026-08-10)
- [x] Automatic sans-serif/serif/script/etc. tagging — extracts `OS/2.sFamilyClass` (the "IBM font class", a standard classification type designers embed in the font) at scan time and auto-applies it as a tag via the existing tags system (e.g. "sans-serif", "oldstyle-serif", "slab-serif", "script"). This is objective metadata already in the file, not AI/ML classification — deliberately distinct from the deprioritized V4 "AI mood tagging" idea. No clean "blackletter/medieval" category exists in this standard; "oldstyle-serif" is the closest objective match. `parser.py`'s `_FAMILY_CLASSES` map covers the ~10 documented top-level classes.
- [x] `fontctl backup <path>` / `fontctl restore <path> [--yes]` — `core/backup.py`, using SQLite's online backup API (`Connection.backup()`), not a raw file copy — safe against an in-use connection. `restore` prompts for confirmation before overwriting the target DB unless `--yes` is passed. Verified round-trip: backed up a library, restored into a fresh DB, all data intact.

## Windows activation (2026-08-11)
- [x] `platforms/windows.py` — real `WindowsActivationProvider` via the GDI `AddFontResourceEx`/`RemoveFontResourceEx` APIs (ctypes, no pywin32 dependency) directly against the original file path — no copy, no registry write, no admin rights needed. Session-wide (not `FR_PRIVATE`) so other apps see it too, but doesn't persist across logoff/reboot, matching the on-demand model. Broadcasts `WM_FONTCHANGE` after each call so already-running apps notice.
- [x] Fixed a real cross-platform correctness gap surfaced while building this: `AddFontResourceEx` is reference-counted (two Add calls need two matching Remove calls), so `activation_service.py`'s `activate_family`/`deactivate_family` now skip the provider call entirely when the DB already records the target state — the DB is the cross-invocation source of truth, not any per-provider state. Regression tests added (`test_activate_family_is_idempotent_against_the_provider` etc.).
- [x] **Verified on real hardware**, and the verification itself surfaced a good lesson: synthetic `FontBuilder` test fonts pass fontTools/Pillow parsing but are rejected by GDI's stricter loader (`AddFontResourceEx` returned 0) — had to test with genuine font files instead. Also found that `System.Drawing.Text.InstalledFontCollection` (GDI+) doesn't reliably reflect classic GDI's `AddFontResourceEx`/`RemoveFontResourceEx` state — verified instead via `EnumFontFamiliesEx` (the same GDI subsystem the provider itself uses): a non-preinstalled font (DejaVu Sans / Inconsolata) went not-found → found → not-found across activate/deactivate through the actual `fontctl` CLI, not just the raw API.
- [x] `platforms/windows.py`'s `is_active()` raises `NotImplementedError` with an explanation — there's no GDI API to query `AddFontResourceEx` registration by path, so it's not implementable honestly; unlike macOS's symlink check, this doesn't block anything since `activation_service.py` never calls `is_active()` (it uses the DB instead).

## Activation Sets (2026-08-11)
- [x] `fontctl set activate <name>` / `fontctl set deactivate <name>` — activates/deactivates every face in a collection at once. Sugar over `collections`, same pattern as Favorites: no new schema, an "activation set" is just a collection used this way (`fontctl collection create`/`add` to build it). Refactored `activation_service.py` to extract a shared `_apply_activation` helper behind both family- and set-level activation, so the reference-count-safe idempotency check (skip the provider call when the DB already says the file is in the target state) applies uniformly — previously only `activate_family`/`deactivate_family` had it. `ActivationResult.family` renamed to `.label` since the same result type now represents either a family name or a set name. **Verified on real hardware**: two real fonts (DejaVu Sans, Inconsolata) activated together and deactivated together with single commands.

## 4-State Model (2026-08-11)
- [x] `fontctl disable <family>` / `fontctl enable <family>` — the schema's `available`/`installed`/`active`/`disabled` states are now all real. `available` stays implicit (no `activations` row — matches how the code already treated untouched fonts). `disabled` has actual teeth: `disable_family` deactivates first if currently active, then marks disabled; `_apply_activation` (shared by `activate_family`/`activate_set`) refuses to activate a disabled file, reporting a clear per-file error rather than silently going through. `enable_family` clears the flag without itself re-activating anything.
- [x] `fontctl info` now shows each file's activation state (`[available]`/`[installed]`/`[active]`/`[disabled]`) — a real gap: after building three activation providers and activation sets, `info`/`list` still showed nothing about activation status until now. `query.get_family_detail` gained an optional `platform_name` param (defaults to the current OS) and joins against `activations`.
- [x] **Verified on real hardware**: full lifecycle on a real font — available → active → disabled (which deactivated it on the OS first) → activate attempt correctly refused → enable → active again.

- [x] Re-running `activate --for` on an already-active font now refreshes/extends its expiry (or clears it, with plain `activate`) without re-touching the OS — the existing reference-count-safe idempotency skip still applies to the provider call, but the DB write for `expires_at` always happens.
- [x] `fontctl info` shows the expiry time alongside activation state when set.
- [x] **Verified on real hardware**: activated a real font with `--for 30m`, confirmed `deactivate-expired` correctly leaves it alone before expiry and deactivates it once the stored expiry is moved into the past.

## Startup State Restore (2026-08-11)
- [x] `fontctl startup` — re-applies every font the library says should be active, for the current platform. Mainly matters on Windows: `AddFontResourceEx` registration is session-only and doesn't survive a reboot (per `platforms/windows.py`'s own docstring), so right after login the DB says "active" while the OS has already forgotten. macOS/Linux persist their activation symlinks on disk across reboot on their own, so running this there is a harmless no-op re-assert.
- [x] Deliberately bypasses the normal "skip the OS call if the DB already says active" idempotency check that `activate_family`/`activate_set` use — that check exists to avoid double-registering with Windows' reference-counted API, but it's exactly wrong for this function's whole purpose (reconciling "DB says active" with "OS actually forgot"). Preserves any existing `expires_at` when re-marking a file active, so a temporary activation that survives a reboot still expires on schedule.
- [x] **Verified on real hardware** with the actual reboot scenario, not just a mock: activated a real font, then called `RemoveFontResourceExW` directly (bypassing the DB entirely, simulating exactly what a reboot does) so the OS no longer had it registered while the DB still said `active`. `EnumFontFamiliesEx` confirmed the font was gone; `fontctl startup` correctly detected and re-registered it, confirmed found again afterward.
- [x] Deliberately **not** a background daemon or login-item installer — same reasoning as `deactivate-expired`, noted together in TODO.md as needing a documented per-OS scheduling recipe (Task Scheduler/launchd/cron/login script).

## Conflict Handling (2026-08-11) — completes V1.5 Activation Manager
- [x] `fontctl conflicts` — reports faces (family+style) backed by 2+ files with *different* content (`core/conflicts.py`). Distinct from `fontctl duplicates` (byte-identical files — harmless, activating either gives the same result) and from the schema's own "a face can have more than one file" allowance (meant for ttf+otf pairs of the *same* font). A real conflict is different fonts claiming the same identity — the case that's actually ambiguous to the OS/apps.
- [x] Activation now refuses to let two different files under the same face be simultaneously active: `_apply_activation` checks the DB (including uncommitted writes earlier in the same transaction, so it catches conflicts within one `activate_family`/`activate_set` call too, not just across separate invocations) and reports a clear per-file error for the loser rather than silently double-registering. The winner is deterministic (lowest `font_file.id`, i.e. first ingested) — pinned down with a test, and noted in TODO.md that there's currently no way to deliberately activate the *other* file instead without a not-yet-built per-file activation command.
- [x] **Verified on real hardware** with two genuinely different real font files reporting the same family+style (copied a real font, appended trailing padding bytes to change its content_hash while fontTools/GDI still parse it fine) — `fontctl conflicts` correctly flagged the pair, `fontctl activate` genuinely activated one on this Windows machine and refused the other with a clear message, never touching the OS for the refused file.
- [x] **V1.5 — Activation Manager is now fully done**: 4-state model, activation sets, temporary activation, startup state restore, conflict handling — all five pieces from the original roadmap sketch are implemented and tested, three real `ActivationProvider`s exist (macOS + Windows confirmed on hardware, Linux unit-tested).

## Smart Collections (2026-08-11)
- [x] `core/smart_collections.py`: a small DNF query language over face/file/tag fields — `field:value` terms space-separated are ANDed, groups split on ` OR ` (case-insensitive) are ORed. No parens, no mixed AND/OR precedence — matches the proposal's own "cheap query language, not NLP" framing (same spirit as `fontctl search`). Fields: `family`, `style`, `foundry`, `tag`, `weight` (numeric), `width`, `source`, `license`, `version`; a bare word matches family/style/foundry/tag like search's free-text term. Unknown fields raise clearly rather than silently matching nothing.
- [x] `fontctl collection create-smart <name> <query>` — uses the schema's `collections.is_smart`/`smart_query` columns, which existed unused since the original schema freeze (exactly the "predict the field, add logic later" pattern already used for the 4-state activation model). Query is validated at creation time so a typo fails immediately, not the first time something reads the collection.
- [x] Smart collections are transparent everywhere regular collections work — no special-casing needed elsewhere. `list_collection_faces`/`list_collection_face_ids`/`list_collections`'s face_count all check `is_smart` internally and evaluate the query live instead of reading `collection_faces` (which stays empty for smart ones — membership can't be stored, it changes as the library changes). This means `fontctl set activate/deactivate` already works on a smart collection for free, since activation sets were already sugar over collections. Manually add/remove-ing a face on a smart collection is rejected with a clear error (its membership isn't yours to edit).
- [x] **Verified on real hardware**: created a smart collection (`family:DejaVu OR family:Inconsolata`), confirmed it found the right 2 real fonts and *not* a third real font added afterward that didn't match; `fontctl set activate` on it genuinely activated both via the real Windows GDI API. Also surfaced an honest, expected limitation while testing with `tag:sans-serif`: a real font (DejaVu Sans) has `OS/2.sFamilyClass` unset (0), so the auto-classification tag was never applied — not a bug, confirms the PANOSE TODO note about inconsistent real-world metadata.

## License Metadata + Conflict Detection (2026-08-11)
- [x] `core/licenses.py`: `classify_license` maps the already-extracted raw license text (name table nameID 13) to a short category (OFL-1.1, Apache-2.0, LGPL, GPL, MIT, Creative Commons, Freeware, Shareware) via keyword matching — `None` if there's no license text at all, `"Unknown"` if there's text but nothing recognized. Deliberately **not** auto-tagged like `family_class`: license can legitimately differ between files under the same face (that's exactly the conflict this feature looks for), so tagging at the face level would silently misrepresent disagreeing files.
- [x] `fontctl licenses` reports faces whose files disagree on license category — e.g. one classifies OFL-1.1, another Apache-2.0. `fontctl info` now also shows each file's classified license label (the raw text is usually a full paragraph, unsuitable for a single CLI line — this is exactly why classification earns its place here, not just cosmetic).
- [x] **Verified on real hardware — and this is where it earned its keep**: `fontctl info` on real, unmodified fonts correctly showed Inconsolata/Source Code Pro as `OFL-1.1` (real embedded license text). But DejaVu Sans came back `Commercial/Proprietary` — wrong; DejaVu is a genuinely free font. Root cause: the original signature list included `"all rights reserved"` → Commercial/Proprietary, but that phrase is standard copyright-ownership boilerplate ("Copyright (c) 2003 by Bitstream, Inc. All Rights Reserved.") that appears in plenty of fully permissive licenses too, immediately followed by a broad rights grant. **Fixed by removing that signature** rather than trying to make the matching smarter (e.g. checking for permission-granting language nearby) — a wrong confident answer is worse than an honest `"Unknown"` for something with real licensing implications. Re-verified: DejaVu Sans now correctly shows `Unknown`. Added a regression test with the exact real license text. Noted in TODO.md as a pattern to watch for if more signatures turn out unreliable.

## Language Coverage — first item picked up in a new session (2026-08-11)
- [x] `fontctl language <family> <style>` — Unicode *script* coverage (`core/language_coverage.py`), grouping the already-parsed `font_glyphs.unicode_codepoint` values by Unicode script via `fontTools.unicodedata` (the same bundled UCD used nowhere else yet in this codebase, zero new dependency). No filter: full script breakdown sorted by glyph count. `--script <query>` accepts either an ISO 15924 code (`Grek`) or an English script name (`Greek`, case-insensitive) and reports supported/glyph_count for just that one.

## PANOSE Fine Classification (2026-08-11)
- [x] **Checked the real-library concern before building, per TODO.md's own caveat**: scanned all 323 real fonts in `C:\Windows\Fonts` and found 319 (98.8%) have a non-zero `OS/2.panose` vector — the opposite of the worry that motivated deferring this item (which was based on DejaVu Sans's `sFamilyClass` being unset, a different field). Went ahead on that evidence.
- [x] `core/panose.py` (`classify_panose`) decodes the 10-byte PANOSE vector into one fine-grained tag: for `bFamilyType == 2` (Latin Text, the common case for body/display fonts), decodes `bSerifStyle` into 14 specific styles (cove, obtuse-cove, square-cove, square, thin, oval, exaggerated, triangle, normal-sans, obtuse-sans, perp-sans, flared, rounded) — finer than `sFamilyClass`'s single flat "sans-serif"/"serif" buckets. For the other family kinds (hand-written/decorative/symbolic), decodes only `bFamilyType` itself — each of those kinds has its own byte-2 meaning table, not decoded here (same "ship the well-understood common case honestly" call as license classification, rather than guessing at three more curated tables). All-zero/unset PANOSE (still ~1% of real fonts) yields no tag, same treatment as `sFamilyClass == 0`.
- [x] Wired into `parser.py` (new `ParsedFont.panose_class` field) and auto-tagged at scan time in `ingest.py`, identically to the existing `family_class` auto-tag — so the new tags work for free everywhere tags already do: `fontctl tag find`, `fontctl search`, and smart collections (`tag:normal-sans`).
- [x] **Verified on real hardware**, and it's a clean complementary result, not a duplicate: `arial.ttf` tags as `sans-serif` (from `sFamilyClass`) **and** `normal-sans` (from PANOSE, finer); `times.ttf` tags as `oldstyle-serif` **and** `cove`; `comic.ttf` tags as `script` **and** `hand-written`. Confirmed a smart collection (`tag:normal-sans`) correctly matched only Arial among the three.
- [x] 286/286 tests passing.
